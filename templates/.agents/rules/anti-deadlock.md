# Anti-Deadlock & Over-Engineering Defense (The Ponytail Ladder)

> **Защита от зацикливания, галлюцинаций и архитектурного оверинжиниринга.**  
> Гарантирует, что агент не утонет в бесконечных рефакторингах и доводит задачи до компилируемого, работающего состояния.

---

## 1. Лестница Ponytail: Принцип бритвы Оккама

При реализации любой задачи в Unity агент обязан двигаться строго по лестнице простоты:

```text
       [ 4. Custom Complex Architecture ]  <-- Крайняя мера (только по явному запросу)
              ▲
       [ 3. Unity Standard Libraries ]     <-- Unity API, URP, InputSystem, NavMesh
              ▲
       [ 2. C# Standard Library ]          <-- Встроенные типы .NET, Span<T>, Collections
              ▲
       [ 1. YAGNI (You Aren't Gonna Need It) ] <-- Самое простое рабочее решение
```

1. **YAGNI**: Не пиши код на гипотетическое будущее. Если фича не нужна прямо сейчас — не создавай под неё пустые интерфейсы и заделы.
2. **Используй готовое**: движок Unity и C# stdlib уже содержат 90% необходимых решений. Не изобретай собственный планировщик кадров, если есть `UniTask` или Unity Coroutines. Не пиши собственный математический solver, если есть `Mathf` / `Vector3`.
3. **Минимум абстракций**: один конкретный понятный класс лучше, чем фабрика фабрик с пятью интерфейсами и DI-контейнером ради создания двух объектов.
4. **Код ➔ Компиляция ➔ Проверка**: написал код ➔ запустил `unity recompile` ➔ убедился в отсутствии ошибок. Никаких рассуждений без проверки компилятором.

---

## 2. Правило 3 попыток (Anti-Loop Rule)

Если агент встречает ошибку компиляции C# или баг Unity:

1. **Попытка 1**: Внимательно прочитать полный текст ошибки и номер строки. Исправить прямую причину.
2. **Попытка 2**: Если ошибка повторяется — проверить зависимости asmdef, using, версию пакетов в `manifest.json`.
3. **Попытка 3**: Если ошибка не уходит — **ОСТАНОВИТЬСЯ**. Запрещено вслепую делать 4-ю и 5-ю попытку.
   * Агент обязан честно сообщить пользователю суть проблемы, привести диагностику из консоли (`unity command console --level error`) и предложить 2–3 альтернативных пути обхода через `ask_user_question`.

---

## 3. Запрет «тихих» изменений

- Никогда не удаляй существующий рабочий код или чужие классы, если тебя об этом прямо не просили.
- Не пытайся «улучшить» соседний код, не относящийся к текущей задаче, чтобы не внести регрессию в проект.
- Не изменяй настройки проекта (`ProjectSettings/*.asset`) без явного разрешения или системной необходимости.
