# Architecture & Design Standards (True Architecture)

> Архитектурные принципы распределения ответственности, владения состоянием и связности подсистем в Unity.

---

## 1. Разделение Фабрики (`Factory`) и Спавнера (`Spawner`)

Это две принципиально разные ответственности:

- **Фабрика (`Factory`)**:
  - Отвечает *только за создание и сборку объекта*.
  - Знает префаб, инстанцирует его, передает зависимости в объект (`Construct` / `Initialize`) и возвращает готовый экземпляр.
  - **Фабрика не знает**: где на уровне находится спавн-точка, сколько объектов сейчас живо, какой таймер между волнами.
- **Спавнер (`Spawner`)**:
  - Отвечает за *ритм и размещение в игровом мире*.
  - Хранит координаты точек появления, таймеры, интервалы волн, лимиты популяции.
  - Для физического создания сущности использует Фабрику:
  ```csharp
  Enemy enemy = _enemyFactory.Create(spawnPoint.position, spawnPoint.rotation);
  ```

---

## 2. Единый владелец состояния (Single State Owner)

У каждого изменяемого фрагмента данных в игре есть **ровно один класс-владелец**:

- **Кошелек (`Wallet`)** — единственный владелец валюты. Внешний код не пишет напрямую в `_money`, а запрашивает операцию: `wallet.TrySpend(cost)`.
- **Здоровье (`Health`)** — единственный владелец очков прочности.
- **Инвентарь (`Inventory`)** — единственный владелец списка предметов.

**Запрещены круговые зависимости и размазывание логики**:
Если сущность А запрашивает товар у сущности Б, проверка остатка и списание происходят внутри сущности Б, а не силами вызывающей стороны.

---

## 3. Доменная модель против анемичных структур (Rich Domain vs Anemic)

Не превращай игровые классы в пассивные контейнеры данных с десятком публичных геттеров/сеттеров, вокруг которых внешний код делает всю работу:

- ❌ **Плохо (анемичный класс)**:
  ```csharp
  // Внешний контроллер сам проверяет всё подряд и вручную правит чужие поля:
  if (cart.Items.Count < cart.MaxCapacity && warehouse.StockCount >= requestedAmount)
  {
      cart.Items.Add(item);
      warehouse.StockCount -= requestedAmount;
  }
  ```
- ✅ **Правильно (доменная модель с поведением)**:
  ```csharp
  // Логика ограничений инкапсулирована внутри доменных сущностей:
  if (warehouse.TryTake(productId, count, out Product product))
  {
      if (cart.TryAdd(product) == false)
      {
          warehouse.Return(product);
      }
  }
  ```

---

## 4. Принцип разделения интерфейсов (ISP)

Не передавай потребителю «тяжелый» монолитный интерфейс всей системы, если ему требуется одна функция:

- Башне, стреляющей снарядами, не нужен весь `PlayerInventory`. Ей нужен узкий интерфейс `IAmmoProvider`.
- Торговой тележке не нужен доступ ко всему складу `Warehouse`. Ей нужен `IProductCatalog` для просмотра и `IProductDispenser` для получения.
- Это изолирует модули и исключает случайную порчу чужого состояния.

---

## 5. Точка входа (Composition Root & Entry Point)

1. **Никакой самозарождающейся логики**:
   - Хаотичные зависимости между объектами через `Start()` вызывают плавающие баги порядка кадров (`Script Execution Order`).
2. **Явная точка сборки**:
   - Каждая сцена или игровой режим имеет точку входа (`Bootstrap` / `EntryPoint`).
   - Точка входа создает ключевые сервисы, собирает граф зависимостей и запускает цикл игры в строго определенном порядке:
     ```csharp
     public sealed class GameplayBootstrap : MonoBehaviour
     {
         private void Awake()
         {
             // 1. Инициализация хранилищ и конфигов
             // 2. Инициализация UI
             // 3. Спавн игрока и привязка камеры
             // 4. Запуск спавнера волн
         }
     }
     ```

---

## 6. Запрет скрытых синглтонов и статики (No Static Abuse)

1. **Не использовать статическую бизнес-логику**:
   - `GameManager.Instance.Player.Wallet.AddMoney(...)` превращает кодовую базу в клубок нераспутываемых скрытых связей.
   - Зависимости передаются явно: через конструкторы в чистом C#, через метод `Initialize(...)` или через контейнеры внедрения зависимостей.
2. **Исключение**:
   - Чистые математические утилиты без внутреннего состояния (`MathUtility`, `PhysicsUtility`).

---

## 7. Конечные автоматы (FSM) против простыней флагов

Если у сущности (игрок, враг, босс, игровая сессия) больше двух взаимоисключающих состояний:
- **Запрещено** заводить простыню флагов: `bool _isAttacking`, `bool _isStunned`, `bool _isDashing`, `bool _isDead`.
- **Правильно**: выделить состояния в явный конечный автомат (State Machine / FSM) или паттерн State. В любой момент времени активно ровно одно состояние (`IdleState`, `AttackState`, `StunnedState`), переходы между ними валидируются централизованно.
